## 一、架构概览

### 业务流程

```
学生报修创建工单（D_Repair_Ticket）
  │  Status = 待处理, SLA_Level = 普通, Assigned_To = NULL
  │
  ├─ [即时] SP_Assign_Ticket 初始派单
  │     └─ Room_ID → Building_ID → 找本楼维修员
  │         ├─ 有维修员 → 指派, SLA=普通, Deadline=Submit_Time+24h, Status=已派单
  │         └─ 无维修员 → rc=3（配置异常，不擅自派楼长）
  │
  ├─ [维修员] SP_Claim_Ticket 接单（原子 UPDATE 守门，不改状态）
  │     └─ 仅允许 Status=已派单 且 Assigned_To=本人的工单；
  │        开工与否以维修日志是否存在判定（PR #44 裁决 §四-3）
  │
  └─ [维修员] SP_Complete_Repair 完工
        └─ 原子守门（Status=已派单 AND Assigned_To=本人）→ 写维修日志 → 状态=已完成


定时兜底
  ├─ TicketAssignJob（每30秒）扫描 Assigned_To IS NULL → SP_Assign_Ticket
  └─ SlaEscalationJob（每15分钟）扫描普通超时 → SP_Escalate_SLA
       └─ 原子标记 Escalation_Time（只提醒不转派）→ 返回升级清单
          → 应用层经 INotificationService 通知楼长
```

> 注：普通 24 小时、终态"已完成"等取值目前属于 PRD/裁决表待冻结项，以冻结后的裁决为准。

### 并发保护

| 层 | 场景 | 机制 |
|---|---|---|
| SP_Assign_Ticket | 重复/并发派单 | 条件 UPDATE（`Assigned_To IS NULL AND Status='待处理'` → `已派单`）+ `SQL%ROWCOUNT` 检查 |
| SP_Claim_Ticket | 多人抢单 | 自赋值 UPDATE 守门（`WHERE Status='已派单' AND Assigned_To=p_Admin_ID`，不改状态）+ `SQL%ROWCOUNT` |
| SP_Complete_Repair | 重复/越权完工 | 原子 UPDATE 守门（`Status='已派单' AND Assigned_To=p_Admin_ID`）+ UK 冲突 SAVEPOINT 回滚 |
| SP_Escalate_SLA | 多实例并发升级 | `FOR UPDATE SKIP LOCKED`（按 Ticket_ID 排序固定加锁顺序）+ 条件 UPDATE（`Escalation_Time IS NULL`）+ `SQL%ROWCOUNT` 检查 |
| 通知投递 | 多实例重复通知 | 仅升级赢家返回清单；通知主键由通知中心公共服务自己生成 |
| TicketAssignJob / SlaEscalationJob | Job 重复触发 | `[DisallowConcurrentExecution]` + SP 内部幂等 |

### 数据拥有者边界

```
报修工单主数据（D_Repair_Ticket.* 增删改）  ← 刘鸿铭
报修派单/接单/完工（难点⑤ SP）              ← 李昂
通知（D_Notification 及其主键机制）          ← 通知中心模块（INotificationService）
审计（D_Audit_Event 及其主键机制）           ← 待数据库负责人确认（见 DDL 影响说明 §0）
```

难点⑤ 的 SP **不直接写** `D_Notification` / `D_Audit_Event`（原 MAX+1 并发撞主键），
通知经公共服务 `INotificationService.CreateAsync` 投递。

### 2.3 存储过程：SP_Assign_Ticket

**功能**：根据工单所关联的 Room → Building，自动查找维修员进行派单。

**调用方式**：

```sql
DECLARE v_Rc NUMBER;
BEGIN SP_Assign_Ticket(p_Ticket_ID => 101, p_Result_Code => v_Rc); END;
```

**处理流程**：

1. 查工单：`SELECT Room_ID, Submit_Time FROM D_Repair_Ticket WHERE Ticket_ID = p_Ticket_ID`
   - `NO_DATA_FOUND → rc=1`
2. Room_ID → Building_ID：`NO_DATA_FOUND → rc=3`（配置异常）
3. 找本楼维修员：`SELECT Admin_ID FROM D_Admin WHERE Role_Level='维修员' AND Building_ID=... AND ROWNUM=1`
   - 无维修员 → **rc=3**（不擅自回退楼长）
4. 原子派单（待处理→已派单，与迁移 021 CHECK 状态集一致）：
   ```sql
   UPDATE D_Repair_Ticket SET Assigned_To=维修员, SLA_Level='普通', Deadline=Submit_Time+24h, Status='已派单'
   WHERE Ticket_ID=p_Ticket_ID AND Assigned_To IS NULL AND Status='待处理';
   ```
   `SQL%ROWCOUNT = 0 → rc=2`（并发被抢/状态已变更）
5. COMMIT

**返回**：0=成功, 1=工单不存在, 2=已指派或状态不对(并发被抢), 3=无可用维修员

### 2.4 存储过程：SP_Claim_Ticket

**功能**：被指派的维修员接单（并发守门，DORM-27）。**四审起不改状态**——PRD §2.3.4
无'处理中'，开工与否以维修日志是否存在判定（PR #44 裁决 §四-3）。

**处理流程**：

1. 原子守门（自赋值 UPDATE，仅利用行计数判定命中）：
   ```sql
   UPDATE D_Repair_Ticket SET Assigned_To = Assigned_To
   WHERE Ticket_ID=p_Ticket_ID AND Status='已派单' AND Assigned_To=p_Admin_ID;
   ```
   - 公共抢单路径（`Assigned_To IS NULL`）已移除：仅允许被指派的维修员接单
   - 接单为幂等确认：重复接单仍 rc=0，状态保持已派单
2. `SQL%ROWCOUNT = 0 → rc=1`
3. COMMIT

### 2.5 存储过程：SP_Complete_Repair

**功能**：管理员完成维修 + 写入维修日志（DORM-28）。

**处理流程**：

1. `SAVEPOINT sp_complete` — 守门，确保日志 INSERT 失败时状态变更可回滚
2. 原子 UPDATE 守门（已派单→已完成）：
   ```sql
   UPDATE D_Repair_Ticket SET Status='已完成'
   WHERE Ticket_ID=p_Ticket_ID AND Status='已派单' AND Assigned_To=p_Admin_ID;
   ```
   - `SQL%ROWCOUNT = 0` → 再查工单是否存在：不存在 rc=1 / 状态或归属不符 rc=2
3. 写日志：`INSERT D_Repair_Log (Log_ID=SEQ_SLA_LOG.NEXTVAL, Ticket_ID, Admin_ID, Process_Desc, Repair_Result, Resolve_Time)`
   - `DUP_VAL_ON_INDEX → ROLLBACK TO sp_complete; rc=3` — UK (Ticket_ID) 唯一约束捕获并发写入
4. COMMIT

**参数**：`p_Repair_Result`（契约字段 repairResult，可空）、`p_Solve_Time`（可空，默认 SYSDATE）。

**返回**：0=成功, 1=工单不存在, 2=状态不是已派单或非本人, 3=日志写入冲突(UK)

### 2.6 存储过程：SP_Escalate_SLA

**功能**：SLA 升级巡检——普通超时工单**只提醒不转派**，原子标记升级并返回本次升级清单。

**调用方式**（C# 经 `OracleCommand` + SYS_REFCURSOR 读取）：

```sql
DECLARE v_Cur SYS_REFCURSOR;
BEGIN SP_Escalate_SLA(p_Cursor => v_Cur); END;
```

**处理流程**：

1. 游标扫描（单表，满足 FOR UPDATE 要求）：
   ```sql
   SELECT Ticket_ID FROM D_Repair_Ticket
   WHERE Status IN ('待处理','已派单') AND SLA_Level='普通'
     AND Deadline < SYSDATE AND Escalation_Time IS NULL
   ORDER BY Ticket_ID
   FOR UPDATE SKIP LOCKED;
   ```
   - `ORDER BY Ticket_ID` 固定加锁顺序 → 多实例交叉死锁防护
   - `SKIP LOCKED` → 已被其他实例锁定的工单直接跳过，不阻塞
2. 条件 UPDATE 守门 + 行数检查：
   ```sql
   UPDATE D_Repair_Ticket SET Escalation_Time = SYSDATE
   WHERE Ticket_ID = ticket_rec.Ticket_ID AND Escalation_Time IS NULL;
   ```
   - `SQL%ROWCOUNT = 1` → 本会话赢得该工单的升级权，记入返回清单
3. COMMIT
4. 返回本次赢得的工单清单（`Ticket_ID, Room_ID, Assigned_To, Mgr_Admin_ID`）：
   - `Mgr_Admin_ID` = 本楼楼长（无楼长 → NULL，应用层跳过投递）
5. **不写** `D_Notification` / `D_Audit_Event`（数据拥有者边界）；通知由应用层公共服务投递

> **并发结论**：每个工单恰被一个实例升级一次（行锁 + 重读已提交条件），
> 双会话竞态验证见 `test_escalation_race_*.sql`。

### 3.2 服务接口

**文件**：`backend/Services/ISlaDispatchService.cs`

```csharp
public interface ISlaDispatchService
{
    Task<int> AssignTicket(int ticketId);
    Task<int> ClaimTicket(int ticketId, string adminId);
    Task<int> CompleteRepair(int ticketId, string adminId, string content, string? repairResult, DateTime? solveTime);
    Task EscalateSla();
    Task<PagedResult<PendingRepairTicketDto>> GetPendingTickets(string adminId, int page, int pageSize);
}
```

### 3.3 服务实现

**文件**：`backend/Services/SlaDispatchService.cs`

**写操作**：OUT 参数存储过程使用原生 `OracleCommand` + `CommandType.StoredProcedure`，
`OracleDecimal` → `int` 转换；所有写操作均含 `try/finally` 确保 Oracle 连接正确释放。

- `AssignTicket` / `ClaimTicket` / `CompleteRepair`：统一由 `CallResultCode` 私有方法封装 OUT 参数模式
- `EscalateSla`：
  1. 原生命令调用 `SP_Escalate_SLA`，读取 `SYS_REFCURSOR` 输出 → 物化升级清单（先关闭命令/游标再投递通知，避免同连接并发使用）
  2. 逐条调用 `INotificationService.CreateAsync`（`AdminId=楼长`，类型 `报修`）
  3. `BusinessException`（如楼长无有效账户）→ 跳过该条，不阻断巡检
  4. 其他异常（如通知仓储 ORA-01400，develop 基线通知主键机制缺口，见数据库影响说明 §0 #4）
     → `LogError` 记录工单号/房间/楼长，不升级为 500：
     升级标记已由 SP 原子提交，端点返回 500 会让调度方重试，而重试再也扫不到该工单
     （`Escalation_Time` 已非空）→ 提醒永久丢失。难点④ 合入后投递即通。

**查询操作**：`GetPendingTickets` 使用 `SqlQueryRaw<PendingRepairTicketDto>` 直接投影：

```sql
SELECT Ticket_ID AS "TicketId", Student_ID AS "StudentId", ...,
       Escalation_Time AS "EscalationTime"
FROM D_Repair_Ticket
WHERE Assigned_To = {0} AND Status IN ('待处理', '已派单')
ORDER BY CASE SLA_Level WHEN '紧急' THEN 0 ELSE 1 END, Deadline ASC
OFFSET {1} ROWS FETCH NEXT {2} ROWS ONLY
```

- 列别名带引号与 DTO 属性名**精确一致**（Oracle 提供程序列匹配区分大小写）
- 分页直接下推 `OFFSET/FETCH`，**不做** EF `Skip/Take` 二次组合（避免外层引用模型列名 → ORA-00904）
- 总数：`SELECT COUNT(*) AS "Value" ...` + `SqlQueryRaw<int>`（标量查询要求输出列名 "Value"）
- 紧急工单排在前 → 普通工单排在后，同级别按 Deadline 升序；只返回指派给当前管理员的工单

## 四、API 层

**文件**：`backend/Controllers/SlaDispatchController.cs`　**路由前缀**：`api`

### 宿管端（DORM-26~28，RepairStaff 策略）

| 方法 | 路径 | 认证 | 说明 |
|---|---|---|---|
| GET | `/admins/{adminId}/repair-tickets?page=&pageSize=` | RepairStaff | DORM-26 待处理工单列表（紧急优先，分页） |
| POST | `/repair-tickets/{ticketId}/claim` | RepairStaff | DORM-27 接单（仅被指派维修员） |
| POST | `/repair-tickets/{ticketId}/logs` | RepairStaff | DORM-28 完工（写维修日志） |

- **授权**：`RepairStaff` 策略 = `admin`（楼长）/ `repairman`（维修员）/ `super_admin`（超级管理员），
  role claim 映射见 [七、授权模型](#七授权模型)
- 管理员身份通过 `ResolveAdminId()` 从 JWT → `Account_ID` → `D_User_Account.Admin_ID` 解析；
  DORM-26 的 URL `adminId` 必须与 JWT 解析结果一致，否则返回 403
- DORM-28 请求体：`{ content(必填≤500), repairResult(可选，枚举校验), solveTime(可选) }`
  - `repairResult` 合法值：`已修复` / `需更换配件` / `无法修复`；非法值 → 400，不触达服务层
- 接单/完工 rc 映射：0=成功 / 1=工单不存在 / 2=状态或归属不符 / 3=日志写入冲突

| 方法 | 路径 | 认证 | 说明 |
|---|---|---|---|
| POST | `/internal/scheduler/assign-ticket?ticketId=` | ServiceKeyAuth | 兜底派单（文档化扩展，非锁定契约） |

## 七、授权模型

**文件**：`backend/Security/AuthPolicies.cs`

role claim 取值沿用前端 mock 的英文小写约定，与 `D_Admin.Role_Level` 映射：

| role claim | D_Admin.Role_Level | 说明 |
|---|---|---|
| `admin` | 楼长 | 宿管端管理员 |
| `repairman` | 维修员 | 难点⑤ DORM-26~28 的执行者 |
| `super_admin` | 超级管理员 | 全局管理 |
| `student` | — | 学生（不进入宿管端策略） |

策略定义（`AuthPolicies.Register` 统一注册，Program.cs 与单元测试共用同一份定义）：

| 策略 | 允许角色 | 适用范围 |
|---|---|---|
| `DormAdmin` | admin, super_admin | 宿管端通用写操作（既有策略，未改动） |
| `RepairStaff` | admin, repairman, super_admin | 难点⑤ DORM-26~28（三审新增） |

登录模块落地时须按上表签发 role claim；`MapInboundClaims=true` 下 JWT `role` 声明自动映射为 `ClaimTypes.Role`。

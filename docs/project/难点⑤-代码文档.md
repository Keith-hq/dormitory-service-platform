## 一、架构概览

### 业务流程

```
学生报修创建工单（D_Repair_Ticket）
  │  Status = 待处理, SLA_Level = 普通, Assigned_To = NULL
  │
  ├─ [即时] SP_Assign_Ticket 初始派单
  │     └─ Room_ID → Building_ID → 优先找本楼维修员
  │         ├─ 有维修员 → 指派, SLA=普通, Deadline=Submit_Time+24h
  │         └─ 无维修员 → 指派楼长, SLA=紧急, Deadline=Submit_Time+12h
  │
  ├─ [管理员] SP_Claim_Ticket 接单（原子 UPDATE 守门）
  │     └─ Status 待处理→处理中, 只有指派给本人或未指派的才能接
  │
  └─ [管理员] SP_Complete_Repair 完工
        └─ 写维修日志(D_Repair_Log) → 状态=已完成


定时兜底
  ├─ TicketAssignJob（每30秒）扫描 Assigned_To IS NULL → SP_Assign_Ticket
  └─ SlaEscalationJob（每15分钟）扫描普通超时 → SP_Escalate_SLA
       └─ 升级为紧急 + 转派楼长 + Deadline 重置12h
```

### 并发保护

| 层 | 场景 | 机制 |
|---|---|---|
| SP_Assign_Ticket | 重复派单 | SELECT 检查 Assigned_To 非空 → 幂等返回 rc=2 |
| SP_Claim_Ticket | 多人抢单 | `UPDATE WHERE Status='待处理' AND (Assigned_To=p_Admin_ID OR Assigned_To IS NULL)` + `SQL%ROWCOUNT` |
| SP_Complete_Repair | 重复完工 | SELECT Status 检查 → '已完成' 返回 rc=2（幂等） |
| SP_Complete_Repair | 同日多日志 | INSERT D_Repair_Log 的 UK (Ticket_ID) + `DUP_VAL_ON_INDEX` 捕获 → rc=3 |
| TicketAssignJob | Job 重复触发 | `[DisallowConcurrentExecution]` + SP 内部幂等 |

### 事务边界

```
报修工单主数据（D_Repair_Ticket.* 增删改）  ← 刘鸿铭
报修派单/接单/完工（难点⑤ SP）              ← 李昂
                                          两者通过 SP 接口隔离
```

### 2.3 存储过程：SP_Assign_Ticket

**文件**：`database/sp/sp_sla_dispatch.sql`

**功能**：根据工单所关联的 Room → Building，自动查找维修员进行派单。无可用维修员时回退到楼长（紧急级别）。

**参数**：

| 参数 | 类型 | 说明 |
|---|---|---|
| p_Ticket_ID | NUMBER | 报修工单 ID |
| p_Result_Code | OUT NUMBER | 0=成功, 1=工单不存在, 2=已指派(幂等), 3=无可用管理员 |

**调用方式**：

```sql
DECLARE rc NUMBER;
BEGIN SP_Assign_Ticket(1, rc); DBMS_OUTPUT.PUT_LINE('rc=' || rc); END;
```

**处理流程**：

1. `SELECT Room_ID, Submit_Time, Assigned_To FROM D_Repair_Ticket` — 取工单信息，`NO_DATA_FOUND → rc=1`
2. 幂等检查：`IF Assigned_To IS NOT NULL → rc=2, RETURN` — 已指派则跳过
3. `SELECT Building_ID FROM D_Room WHERE Room_ID = v_Room_ID` — 关联楼栋
4. 优先派维修员：`SELECT Admin_ID FROM D_Admin WHERE Role_Level='维修员' AND Building_ID=v_Building_ID`
   - 找到 → `UPDATE SET Assigned_To=维修员, SLA_Level='普通', Deadline=Submit_Time+24h`
5. 无维修员 → 回退楼长：`SELECT Admin_ID FROM D_Admin WHERE Role_Level='楼长' AND Building_ID=v_Building_ID`
   - 找到 → `UPDATE SET Assigned_To=楼长, SLA_Level='紧急', Deadline=Submit_Time+12h`
   - 找不到 → `rc=3`（无可用管理员）
6. COMMIT

### 2.4 存储过程：SP_Claim_Ticket

**功能**：管理员接单，原子 UPDATE 防并发抢单。只有状态为"待处理"且指派给本人（或未指派）的工单才能成功。

**参数**：

| 参数 | 类型 | 说明 |
|---|---|---|
| p_Ticket_ID | NUMBER | 工单 ID |
| p_Admin_ID | VARCHAR2 | 接单管理员 ID |
| p_Result_Code | OUT NUMBER | 0=成功, 1=工单不存在/状态不对/已被抢 |

**处理流程**：

1. 原子抢单：
   ```sql
   UPDATE D_Repair_Ticket
   SET Status = '处理中'
   WHERE Ticket_ID = p_Ticket_ID
     AND Status = '待处理'
     AND (Assigned_To = p_Admin_ID OR Assigned_To IS NULL)
   ```
2. `SQL%ROWCOUNT = 0 → rc=1, RETURN` — 已被他人抢走或状态变更
3. COMMIT

**关键设计**：不用 `SELECT FOR UPDATE` 加锁，直接靠 `UPDATE WHERE` 的原子性 + `SQL%ROWCOUNT` 判断。Oracle 内部对同一条记录的 UPDATE 是串行的，第二条 UPDATE 的行数判定自然为 0。

### 2.5 存储过程：SP_Complete_Repair

**功能**：管理员完成维修，写入维修日志并更新工单状态。一单一日志（UK 约束保证）。

**参数**：

| 参数 | 类型 | 说明 |
|---|---|---|
| p_Ticket_ID | NUMBER | 工单 ID |
| p_Admin_ID | VARCHAR2 | 完工管理员 ID |
| p_Process_Desc | VARCHAR2 | 维修处理描述 |
| p_Result_Code | OUT NUMBER | 0=成功, 1=工单不存在, 2=已完成(幂等), 3=日志写入冲突 |

**处理流程**：

1. `SELECT Status FROM D_Repair_Ticket WHERE Ticket_ID = p_Ticket_ID` — `NO_DATA_FOUND → rc=1`
2. `IF Status = '已完成' → rc=2, RETURN` — 幂等，已完成不重复写
3. 先写日志：`INSERT D_Repair_Log (Log_ID, Ticket_ID, Admin_ID, Process_Desc, Resolve_Time)`
   - `DUP_VAL_ON_INDEX → rc=3, RETURN` — UK (Ticket_ID) 唯一约束捕获并发写入
4. 再改状态：`UPDATE D_Repair_Ticket SET Status='已完成' WHERE Ticket_ID = p_Ticket_ID`
5. COMMIT

> **为什么先写日志再改状态？** 日志写入受 UK 唯一约束保护，是真正的"守门"操作。如果先改状态再写日志，并发场景下可能出现"状态已改但日志未写入"的脏窗口。

### 2.6 存储过程：SP_Escalate_SLA

**功能**：SLA 升级巡检，将已超时的普通工单升级为紧急并转派楼长。

**调用方式**：

```sql
BEGIN SP_Escalate_SLA; END;
```

**处理流程**：

1. 游标扫描：
   ```sql
   SELECT t.Ticket_ID, r.Building_ID
   FROM D_Repair_Ticket t
   JOIN D_Room r ON t.Room_ID = r.Room_ID
   WHERE t.Status IN ('待处理', '处理中')
     AND t.SLA_Level = '普通'
     AND t.Deadline < SYSDATE
   ```
2. 循环内：`SELECT Admin_ID FROM D_Admin WHERE Role_Level='楼长' AND Building_ID=ticket_rec.Building_ID`
   - `NO_DATA_FOUND → CONTINUE` — 该楼无楼长则跳过
3. 升级：`UPDATE SET SLA_Level='紧急', Assigned_To=楼长, Deadline=SYSDATE+12h`
4. COMMIT

> **设计注意**：只升级"普通"超时工单。"紧急"已是最高的 SLA 级别，即使超时也不再升级（无更高等级可升级到）。

## 三、C# 服务层

### 3.1 数据模型

两个新增实体，均在 `backend/Models/` 下：

| 模型 | 对应表 | 关键属性 |
|---|---|---|
| RepairTicket | D_Repair_Ticket | TicketId, StudentId, RoomId, IssueDesc, SubmitTime, Status, SlaLevel, Deadline, AssignedTo |
| RepairLog | D_Repair_Log | LogId, TicketId, AdminId, ProcessDesc, ResolveTime |

### 3.2 服务接口

**文件**：`backend/Services/ISlaDispatchService.cs`

```csharp
public interface ISlaDispatchService
{
    Task<int> AssignTicket(int ticketId);
    Task<int> ClaimTicket(int ticketId, string adminId);
    Task<int> CompleteRepair(int ticketId, string adminId, string processDesc);
    Task EscalateSla();
    Task<List<RepairTicket>> GetPendingTickets(string adminId);
}
```

### 3.3 服务实现

**文件**：`backend/Services/SlaDispatchService.cs`

**写操作**：OUT 参数存储过程使用原生 `OracleCommand` + `CommandType.StoredProcedure`，`OracleDecimal` → `int` 转换。

- `AssignTicket` / `ClaimTicket` / `CompleteRepair`：统一由 `CallResultCode` 私有方法封装 OUT 参数模式
- `EscalateSla`：无 OUT 参数，使用 `ExecuteSqlRawAsync("BEGIN SP_Escalate_SLA; END;")`
- 所有写操作均含 `try/finally` 确保 Oracle 连接正确释放

**查询操作**：`GetPendingTickets` 使用 `FromSqlRaw` 显式列别名：

```sql
SELECT Ticket_ID AS TicketId, Student_ID AS StudentId, ...
FROM D_Repair_Ticket
WHERE Assigned_To = {0} AND Status IN ('待处理', '处理中')
ORDER BY CASE SLA_Level WHEN '紧急' THEN 0 ELSE 1 END, Deadline ASC
```

- 紧急工单排在前 → 普通工单排在后，同级别按 Deadline 升序
- 只返回指派给当前管理员的工单

### 宿管端（DORM-26~28）

| 方法 | 路径 | 认证 | 说明 |
|---|---|---|---|
| GET | `/repair-tickets/pending` | DormAdmin | DORM-26 待处理工单列表（紧急优先） |
| POST | `/repair-tickets/{ticketId}/claim` | DormAdmin | DORM-27 接单（原子抢单） |
| POST | `/repair-tickets/{ticketId}/complete` | DormAdmin | DORM-28 完工（写入维修日志） |

- 管理员身份通过 `ResolveAdminId()` 从 JWT → `Account_ID` → `D_User_Account.Admin_ID` 解析
- Complete 请求体含 `[Required][StringLength(500)] ProcessDesc`，校验消息为 "维修描述不能为空" / "维修描述最长500字"
- 接单返回中文提示：成功 / "工单不存在、已被他人接走或状态不是待处理"
- 完工 rc 映射：0=维修完成, 1=工单不存在, 2=工单已完成, 3=日志写入冲突

### Internal 端点

| 方法 | 路径 | 认证 | 说明 |
|---|---|---|---|
| POST | `/internal/scheduler/assign-ticket?ticketId=` | ServiceKeyAuth | 兜底派单（Quartz 30s 扫描调用） |

- 返回 `ApiResponse.Ok` 含 `resultCode`，确认执行状态

## 五、定时任务

**文件**：`backend/Jobs/SlaJobs.cs`

### TicketAssignJob

| 属性 | 值 |
|---|---|
| Job | TicketAssignJob |
| cron | `0/30 * * * * ?`（每 30 秒） |
| 时区 | China Standard Time |
| 并发 | `[DisallowConcurrentExecution]` |

**流程**：

1. `FromSqlRaw` 查询 `Assigned_To IS NULL` 的工单
2. 逐个调用 `ISlaDispatchService.AssignTicket(ticketId)`
3. SP 内部幂等 — 即使 Assign 已调过，重复调用也安全

> **兜底设计**：正常流程下学生报修创建工单后即时调用 `SP_Assign_Ticket`。本 Job 为兜底：防止直接 INSERT 工单或系统调用失败导致漏派。30 秒间隔在"及时性"与"数据库压力"之间取得平衡。

### SlaEscalationJob

| 属性 | 值 |
|---|---|
| Job | SlaEscalationJob |
| cron | `0 0/15 * * * ?`（每 15 分钟） |
| 时区 | China Standard Time |
| 并发 | `[DisallowConcurrentExecution]` |

直接调用 `ISlaDispatchService.EscalateSla()` → `SP_Escalate_SLA`，传入 ServiceKeyAuth 绕过 JWT 认证。

## 六、注册与配置

### 6.1 Program.cs

```csharp
// 第 83 行：注册服务
builder.Services.AddScoped<ISlaDispatchService, SlaDispatchService>();

// Quartz 块中注册两个 Job
// 难点⑤ SLA派单补齐：每 30 秒
var assignKey = new JobKey("TicketAssignJob");
q.AddJob<TicketAssignJob>(opts => opts.WithIdentity(assignKey));
q.AddTrigger(opts => opts.ForJob(assignKey).WithIdentity("TicketAssignTrigger")
    .WithCronSchedule("0/30 * * * * ?", x => x.InTimeZone(tz)));

// 难点⑤ SLA升级巡检：每 15 分钟
var escalateKey = new JobKey("SlaEscalationJob");
q.AddJob<SlaEscalationJob>(opts => opts.WithIdentity(escalateKey));
q.AddTrigger(opts => opts.ForJob(escalateKey).WithIdentity("SlaEscalateTrigger")
    .WithCronSchedule("0 0/15 * * * ?", x => x.InTimeZone(tz)));
```

- 日期：2026-08-13
- 背景：接口认领 v0.4 决策，退宿清算 5 个接口（DORM-11/35/36/37/38）自李昂转刘润东，床位表数据由刘润东唯一负责。
- 状态：✅ 已确认（2026-08-13，组长 + 刘润东均同意本文档第三部分方案）。落地改动见 SP v1.2（database/sp/sp_fee_sharing.sql）与 [难点⑥-SP调用说明-给刘润东.md](难点⑥-SP调用说明-给刘润东.md)。

## 一、接口转移后的分工（请组长确认）

按接口认领 v0.4，退宿清算 5 个接口（DORM-11/35/36/37/38）从我这转给刘润东，床位表数据由刘润东唯一负责，我不再碰床位写入。

我保留并负责的只有一块：结算金额计算（calc-checkout，SP_Calc_Checkout_Fee），难点①已经交付，只读床位表，不写。

所以我理解的分工是：

1. 刘润东：退宿流程全链路——三步校验（水电费缴清、快递取走、共享物品归还）、退宿办理、床位和房间状态写入。
2. 我（李昂）：结算金额计算 calc-checkout，保证费用明细只产生一份，金额唯一来源是我这。

请组长确认这样划分有没有问题，确认后我更新接口认领表。

## 二、需要和刘润东确认的问题

1. 调用顺序。方案稿里是先清算后写退宿日期，但 calc 在退宿日期还没写的时候会回退用 SYSDATE，结算口径会有偏差。建议改成先写退宿日期、再调 calc。
2. 事务边界。calc 内部自带 COMMIT，放进退宿事务里会提前提交，破坏原子性。要么走最终一致性，要么我改 SP 去掉 COMMIT、由外层统一提交，刘润东倾向哪种。
3. 调用方式。刘润东的 settle 直接调 SP，还是走我的接口，定一下，我这边两种都支持。
4. 幂等口径。我这侧已用唯一索引（Fee_ID + Student_ID + Bill_Type）兜底，重复调用静默跳过；刘润东 settle 侧也要保证同一退宿流程不重复触发结算，否则会出重复记录。

## 三、我的方案

1. 边界：刘润东的 settle 只管流程和状态，金额一律以 calc 计算结果为准，不重复计算。
2. 顺序：settle 先写 CheckOut_Date，再调 calc，保证按实际退宿日期结算。
3. 事务：我改 SP 去掉内部 COMMIT，由刘润东的退宿事务统一提交，床位、房间、费用三处要么全成要么全不成。
4. 调用：刘润东直接调 SP 就行，我把签名和参数说明整理给他；接口保留给定时任务和人工补算场景。
5. 验收：按集成测试 IT-C10-004，两入口不重复结算、金额一致只扣一次、库里无重复扣款记录。

如果方案可以，我这边改 SP 是小改动，明天（8/14）就能配合联调。

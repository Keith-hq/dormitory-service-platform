## 二、难点① 水电分摊

### 问题描述

财务按月录入房间水电费总额到 D_Utility_Fee，但一个房间住多人且入住时长不一，需要将总额公平分摊到每个学生。当前仅有房间级账单，缺少个人级账单，无法追踪个人欠费状态。

### 解决方法

采用**人天数比例分摊算法**：

- 某人应付 = 房间总额 × (该人入住天数 ÷ 房间总人天数)
- 总人天数 = Σ(该房间每位在住学生的当月入住天数)
- 单人天数 = MIN(月末, 退宿日期) − MAX(月初, 入住日期) + 1

所有个人分摊之和恰好等于房间总额，不存在尾差亏空。

### 触发时机及数据变动

**触发 A — 每月 1 日（Quartz 定时任务）：**
1. 读取 D_Bed_Allocation，计算每位在住学生的当月入住天数
2. 读取 D_Utility_Fee 当月账单
3. 按比例算出每人 Water_Share 和 Power_Share
4. 向 D_Fee_Detail 批量插入分摊记录，Bill_Type = '月度'

**触发 B — 学生退宿时（由难点⑥ CheckOutService 调用）：**
1. 计算该学生本月 1 日至退宿日的入住天数
2. 重新统计该房间本月当前总人天数
3. 向 D_Fee_Detail 插入分摊记录，Bill_Type = '退宿'
4. D_Bed_Allocation.CheckOut_Date = SYSDATE
5. D_Room.Occupancy = Occupancy − 1

### 涉及的表

| 角色 | 表 |
|---|---|
| 读取 | D_Bed_Allocation、D_Utility_Fee、D_Room |
| 写入 | D_Fee_Detail（新表）、D_Bed_Allocation（退宿时） |
| 更新 | D_Room.Occupancy（退宿时） |

## 三、难点② 账单划扣与断电判定

### 问题描述

难点① 已生成个人分摊账单，但缺少两个机制：(1) 自动从学生钱包扣款；(2) 电费欠费时执行断电惩戒。

### 解决方法

**自动划扣（每月 1/2/3 日三次尝试）：**

每次遍历 D_Fee_Detail 中 Is_Paid = '否' 的账单：
- 检查 D_Student.Balance
- 余额 ≥ 应付合计 → 扣减 Balance、Is_Paid 改为"是"、写入 D_Wallet_Log（Type = '自动扣款'）
- 余额不足 → 不扣款、Is_Paid 保持"否"
- 每次扣款写入唯一 Idempotent_Key（Fee_Detail_ID + Year_Month），杜绝重复扣款

**断电判定（第 3 日第三次失败后执行）：**

每月 3 日第三次扣款结束后，满足以下条件的房间触发断电：
- 仅看电费：D_Fee_Detail.Power_Share 未缴
- 水费欠缴只影响账单和退宿，不触发断电
- D_Room.Power_Status 置为"断电"

**恢复供电（缴清后 5 分钟内）：**
- 学生充值后自动补扣，或主动点击人工缴费
- 房间全部电费缴清后，5 分钟内 D_Room.Power_Status 恢复"正常"

### 触发时机及数据变动

| 触发 | 时机 | 数据变动 |
|---|---|---|
| A | 每月 1/2/3 日（Quartz） | 遍历未缴账单 → 扣款 → 写钱包流水 → 3 日仍未缴则断电 |
| B | 学生充值后 | Balance 增加 → 补扣所有未缴账单 → 检查是否恢复供电 |
| C | 人工缴费 | 点击缴费 → 扣款 → 写流水 → 成功后 5 分钟内恢复供电 |
| D | 恢复巡检（每分钟） | 检查断电房间 → 全员电费缴清 → 恢复供电 |

### 涉及的表

| 角色 | 表 |
|---|---|
| 修改 | D_Student（加 Balance）、D_Room（加 Power_Status） |
| 新建 | D_Wallet_Log |
| 读取 | D_Fee_Detail |

## 四、难点③ 洗衣机/浴室防冲突预约

### 问题描述

多人同时抢占同一台洗衣机，不加并发控制会导致重复占用。第一版只做洗衣机即时预约，浴室后置。

### 解决方法

**即时占用模式（不支持未来时段预约）：**
1. 学生点击"立即使用" → 系统检查该设施是否空闲（无 Status IN ('已预约','使用中') 的记录）
2. 空闲 → 创建预约记录，Status = '已预约'
3. 15 分钟内未点击"开始使用" → 自动失效，Status = '已失效'，释放设施
4. 点击"开始使用" → Status = '使用中'，Start_Time = NOW，固定使用 60 分钟
5. 可提前结束 → End_Time 记录，Status = '已完成'，释放设施

**并发保护（需 POC 验证）：**
- 锁设施主记录行（模块 3 设施档案表）
- 在锁保护下检查是否有活跃占用记录
- 无冲突 → INSERT D_Facility_Booking → COMMIT
- 有冲突 → ROLLBACK，提示"该设施正在使用中"

### 触发时机及数据变动

| 触发 | 时机 | 数据变动 |
|---|---|---|
| A | 学生即时预约 | 锁设施行 → 检查无冲突 → INSERT（Status='已预约'） |
| B | 15 分钟失效巡检（每分钟） | Status='已预约' AND NOW > Booking_Time + 15min → '已失效' |
| C | 点击开始 | Status='使用中'，Start_Time = NOW |
| D | 60 分钟到或提前结束 | Status='已完成'，End_Time 记录 |

### 涉及的表

| 角色 | 表 |
|---|---|
| 新建 | D_Facility_Booking |
| 锁定 | 模块 3 设施档案表（设施主记录行） |

## 五、难点④ 库存联动事务

### 问题描述

维修消耗配件和共享物品借还需要跨表原子操作——同时修改库存和记录，两步必须一起成功或一起失败。库存语义需严格分离。

### 解决方法

**4 个跨表事务场景：**

| 场景 | 操作 | 涉及表 |
|---|---|---|
| A 维修耗材出库 | 扣库存 + 写维修日志 + 完工单 | 耗材库存 + D_Repair_Log + D_Repair_Ticket |
| B 借出 | Available_Qty −1 + 写借出记录 | D_Shared_Item + D_Item_Loan |
| C 归还 | Available_Qty +1 + 写归还时间 | D_Shared_Item + D_Item_Loan |
| D 逾期扣分 | 扫描逾期记录 + 写信用分流水 | D_Item_Loan + D_Credit_Log |

所有事务统一遵循"锁行 → 校验 → 写表 A → 写表 B → COMMIT（失败则 ROLLBACK）"模式。

**库存语义分离（红线）：**
- D_Asset：固定资产台账（空调、桌椅），只做盘点
- 耗材库存：维修配件（灯泡、水龙头），独立库存概念，与架构师确认实现方式
- D_Shared_Item：共享物品（吹风机、钥匙），只做借还
- 三种库存不混用

### 触发时机及数据变动

全部由用户操作实时触发。事务失败 → ROLLBACK → 返回具体失败原因。

### 涉及的表

| 角色 | 表 |
|---|---|
| 复用 | D_Repair_Log、D_Repair_Ticket、D_Asset（仅固定资产） |
| 新建 | D_Shared_Item、D_Item_Loan、D_Credit_Log |
| 新增概念 | 耗材库存（与架构师确认最终实现方式） |

## 六、难点⑤ SLA 派单

### 问题描述

报修工单需自动派给本楼维修员，超时未处理则升级给楼长。只做一次升级。

### 解决方法

| 等级 | 时限 | 超时动作 | 指派对象 |
|---|---|---|---|
| 普通 | 24 小时 | 升级为"紧急"，通知楼长 | 本楼维修员 |
| 紧急 | 12 小时 | —（不继续升级） | 楼长 |

Quartz 定时任务每 15 分钟扫描 Status ≠ '已完成' AND NOW > Deadline 的工单。

**初始派单逻辑：**
1. 学生提交报修 → D_Repair_Ticket.Status = '待处理'
2. 系统根据 Room_ID → Building_ID → 查 D_Admin（Role_Level = '维修员' AND Building_ID = 该楼栋）
3. Assigned_To = 维修员，SLA_Level = '普通'，Deadline = Submit_Time + 24 小时
4. 若无维修员，直接指派楼长

### 触发时机及数据变动

| 触发 | 时机 | 数据变动 |
|---|---|---|
| A | 学生提交报修 | 查楼栋→维修员→设 Assigned_To/SLA_Level='普通'/Deadline |
| B | Quartz 每 15 分钟巡检 | 扫描普通超时工单 → SLA_Level='紧急'，Assigned_To→楼长，Deadline 重置 +12h |
| C | 管理员处理完成 | Status='已完成' + 写入 D_Repair_Log |

### 涉及的表

| 角色 | 表 |
|---|---|
| 修改 | D_Repair_Ticket（加 SLA_Level、Deadline、Assigned_To）、D_Admin（加 Building_ID） |

## 七、难点⑥ 退宿清算

### 问题描述

学生发起退宿申请时，系统自动完成 3 步校验。全部通过后执行退宿事务：结算当月水电分摊、写入退宿日期、更新房间人数。任一校验不通过则拒绝并告知原因。

### 解决方法

**三步校验（串行，任一步失败即拒绝）：**

| # | 校验项 | 数据来源 | 判定规则 |
|---|---|---|---|
| ① | 水电费缴清 | D_Fee_Detail | 该学生 Is_Paid = '否' 的记录 = 0 |
| ② | 快递全取走 | D_Parcel_Record | 该学生 Pickup_Time IS NULL 的记录 = 0 |
| ③ | 共享物品全归还 | D_Item_Loan | 该学生 Return_Time IS NULL 的记录 = 0 |

**退宿事务（三步校验全部通过后执行）：**
1. SELECT FOR UPDATE 锁定 D_Room 行
2. 调用 FeeSharingService.CalcCheckoutFee 生成退宿分摊
3. D_Bed_Allocation.CheckOut_Date = SYSDATE
4. D_Room.Occupancy = Occupancy − 1
5. D_Checkout_Log 写入（Status = '通过'，三项校验结果分别记录）
6. COMMIT

### 触发时机及数据变动

| 触发 | 时机 | 数据变动 |
|---|---|---|
| A | 学生发起退宿申请 | 依次执行三步校验 → 任一不通过则写 D_Checkout_Log（Status='拒绝'）并返回原因 |
| B | 校验全部通过 | 锁 D_Room → 退宿分摊 → 写 CheckOut_Date → Occupancy−1 → COMMIT |

### 涉及的表

| 角色 | 表 |
|---|---|
| 新建 | D_Checkout_Log |
| 读取 | D_Fee_Detail、D_Parcel_Record、D_Item_Loan |
| 写入 | D_Bed_Allocation.CheckOut_Date |
| 更新 | D_Room.Occupancy − 1 |

## 八、服务接口层

6 个难点各自封装为独立 Service 类，通过依赖注入供模块开发组和其他角色调用。

| 难点 | Service 类名 | 核心方法 | 调用方 |
|---|---|---|---|
| ① 水电分摊 | FeeSharingService | CalcMonthlyFee / CalcCheckoutFee / GetFeeDetail | 定时任务、CheckOutService、报表模块 |
| ② 划扣断电 | BillingService | TryAutoDeduct / ManualPay / CutPower / RestorePower / GetWalletLog | 定时任务、缴费页面 |
| ③ 设施预约 | FacilityBookingSvc | OccupyNow / StartUse / EndUse / CheckExpired | 设施预约页面、定时巡检 |

### 服务间依赖关系

```
CheckOutService
  ├── FeeSharingService.CalcCheckoutFee()
  ├── BillingService（通过 D_Fee_Detail 间接依赖）
  └── InventoryTxnSvc（归还状态校验）

FeeSharingService ← 无依赖（仅读取 D_Bed_Allocation + D_Utility_Fee）
BillingService    ← FeeSharingService（分摊结果）
FacilityBookingSvc ← 无依赖（仅操作 D_Facility_Booking + 设施档案表）
InventoryTxnSvc  ← 无依赖（仅操作库存 + 借还记录表）
SlaDispatchService ← 无依赖（仅操作 D_Repair_Ticket + D_Admin）
```

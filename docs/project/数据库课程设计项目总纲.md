## 3. 课程项目硬性要求

1. **开发环境与技术**：使用集成开发环境 **VS.NET 较新版本**，使用 **C# 语言**，以 **Oracle 18c 或更高版本**作为 DBMS，采用 **Oracle 数据访问组件（ODAC）或 ORM 框架**，开发一个实用信息管理系统（**C/S 或 B/S 均可**）。
   - 参考选题举例：考勤管理系统、车辆管理系统、学生宿舍管理系统、学生学籍管理系统、图书管理系统、商品零售管理系统等。
2. **团队规模**：**10 人一组**（选课人数共\*人，共\*组，只有一组少于 10 人，其余均为 10 人），选出一名组长。由组长牵头，小组成员讨论决定项目选题，确定系统功能。
3. **数据表要求**：**至少 12 张表**，且**符合第三范式（3NF）**。
4. **功能点要求**：**至少 20 个功能点**，其中**至少 15 个功能点必须具有一定的业务逻辑功能**，不能仅仅是针对每个表的增删改查。
   - **重要口径**：\*\*信息的增删改是一个功能点，不是三个功能点\*\*；即 **\*\*信息的增删改查可以列为二个功能点**（例如"学生的增删改"=1 个功能点，"学生的查询"=1 个功能点）。
5. **答辩要求**：答辩时**组的所有成员必须到场，1 人主讲，所有组员都会被提问**；答辩时间**最多 20 分钟**。

## 8. 本项目选题：开发背景与系统需求

**来源**：《高校宿舍后勤与共享生活服务平台 —— 项目开发构想（整合版）》《高校宿舍后勤与共享生活服务系统设计文档》

### 8.1 开发背景与系统定位

- 项目名称：**高校宿舍后勤与共享生活服务平台**
- 系统架构：**B/S 架构**。
- 整体功能需求覆盖：资产维护、住户档案、水电分摊、虚拟钱包、账单划扣、设施预约防冲突、报修流转与派单、库存联动、访客授权、房间投票、共享物品借用、信用分体系、退宿清算、保洁巡检、消费统计报表等，共 **20 项**。
- **难度分布**：约六成为标准增删改查类功能；约四成涉及**定时任务、并发控制、事务联动、状态机流转**等中高复杂度设计。

### 8.2 详细功能数据需求（21 条）

> 以下为《系统设计文档》1.1–1.20 的原始数据需求 + 1.21 组织结构说明，是撰写《系统需求分析文档》的直接素材。

**1.1 楼栋与房间空间管理数据需求**
- 数据需求：Building_ID, Building_Name, Building_Type, Total_Floors；Room_ID, Room_Number, Capacity
- 功能描述：管理员维护宿舍楼基本信息及房间配置。支持按楼栋类型（男/女/混合）和总层数进行房间的批量初始化分配。

**1.2 学院-专业-学生组织架构管理数据需求**
- 数据需求：College_Name, Major_Name, Student_ID, Name, Gender, College
- 功能描述：建立"学院-专业-学生"的三级树状管理体系。录入学生档案时，自动关联所属学院与专业，解决学生行政归属问题。

**1.3 房间内部资产档案入库数据需求**
- 数据需求：Asset_ID, Room_ID, Asset_Name, Quantity, Status
- 功能描述：对房间内的固定资产（如空调、床铺、桌椅）进行登记。系统监控资产状态（正常/损坏/缺失），作为资产盘点和维修报修的基础。

**1.4 宿管人员权限管理数据需求**
- 数据需求：Admin_ID, Admin_Name, Role_Level, Phone
- 功能描述：维护后台管理人员档案，并划分"超级管理员"与"楼长"权限。楼长仅能查看和管理其所属楼栋的数据。

**1.5 住宿分配与床位状态追踪数据需求**
- 数据需求：Allocation_ID, Student_ID, Room_ID, CheckIn_Date, CheckOut_Date, Occupancy
- 功能描述：管理学生入住全过程。当学生成功入住时，D_Room 表中的"当前入住人数（Occupancy）"自动加 1；退宿时自动减 1。

**1.6 水电费账单月度发布数据需求**
- 数据需求：Fee_ID, Room_ID, Year_Month, Water_Fee, Power_Fee, Is_Paid
- 功能描述：财务每月录入房间的水费和电费金额。学生可通过系统查询本宿舍的未缴账单，缴纳后状态由"否"改为"是"。

**1.7 桶装水在线订购记录数据需求**
- 数据需求：Order_ID, Room_ID, Order_Time, Quantity, Status
- 功能描述：学生在线发起订水请求，系统记录订水数量及下单时间。宿管根据订单列表进行配送，并更新状态为"已送达"。

**1.8 维修报修全流程跟踪数据需求**
- 数据需求：Ticket_ID, Student_ID, Room_ID, Issue_Desc, Status
- 功能描述：学生提交文字描述的报修单（如"302 水管漏水"）。系统追踪报修单从"待处理"到"已完成"的状态流转。

**1.9 维修处理日志维护数据需求**
- 数据需求：Log_ID, Ticket_ID, Admin_ID, Process_Desc, Resolve_Time
- 功能描述：维修员在处理完成后录入维修过程反馈及解决时间。此表与报修单形成 **1:1 关联**，确保每一笔报修都有据可查。

**1.10 后勤公告发布系统数据需求**
- 数据需求：Notice_ID, Admin_ID, Title, Content, Publish_Time
- 功能描述：管理员发布停水停电、放假通知等公告。系统按发布时间倒序排列展示在学生端主页。

**1.11 快递代收与取件状态监控数据需求**
- 数据需求：Parcel_ID, Student_ID, Arrive_Time, Pickup_Time, Courier_Company
- 功能描述：驿站或宿管录入快递信息。系统根据"实际取件时间"是否为空来判断该包裹是否已被领走，支持按快递公司进行分类统计。

**1.12 楼栋门禁出入实时记录数据需求**
- 数据需求：Log_ID, Student_ID, Building_ID, Swipe_Time, Direction
- 功能描述：对接物理闸机，实时记录学生的刷卡时间及进出方向。此数据可用于分析楼内人员实时密度，作为消防安全依据。

**1.13 外来访客准入登记管理数据需求**
- 数据需求：Visitor_ID, Building_ID, Visitor_Name, Visit_Reason, Entry_Time, Leave_Time
- 功能描述：门岗录入访客姓名、访问理由及进出时间。系统可筛选出"当前已进入但尚未离开"的访客名单，加强楼栋安全。

**1.14 晚归自动预警系统数据需求**
- 数据需求：Record_ID, Student_ID, Return_Time, Reason
- 功能描述：系统筛选出在规定时间（如 23:30）后返回的学生记录。宿管在晚归登记表中补全晚归原因，用于学期末的纪律评定。

**1.16 节假日离校返校报备数据需求**
- 数据需求：Apply_ID, Student_ID, Leave_Date, Return_Date, Destination, Status
- 功能描述：长假期间学生申报离校去向。辅导员在线审批，系统统计离校总人数及学生所在目的地，确保学生安全动态受控。

**1.17 学生违规违纪处分记录数据需求**
- 数据需求：Record_ID, Student_ID, Room_ID, Vio_Type, Vio_Date, Penalty
- 功能描述：记录学生查寝未归、使用违章电器等行为。记录包括违纪日期及处分结果。

**1.18 退宿财务核算数据需求**
- 数据需求：CheckOut_Date, Is_Paid, Pickup_Time
- 功能描述：学生发起退宿申请。系统自动检索该学生：① 房间水电费是否缴清；② 快递代收是否全部取走。所有校验通过后，才允许录入退宿日期。

**1.19 资产损耗预警统计数据需求**

### 9.2 逻辑设计（表设计归类与关系类型）

**9.2.1 核心强实体**（独立存在、拥有主键、不依赖其他实体）
- D_College（学院表）：学校的硬件组织架构
- D_Major（专业表）：具体的学科分类
- D_Building（楼栋表）：物理存在的建筑
- D_Room（房间表）：具体的物理居住空间
- D_Student（学生表）：系统服务的核心对象
- D_Admin（管理员表）：系统权限的拥有者与管理员
- D_Asset（资产表）：作为固定资产，视为独立实体管理

**9.2.2 弱实体 / 业务事件实体**（全参与、强制依赖核心实体，避免菱形悬空）
- D_Repair_Ticket（报修申请表）：依赖"学生"和"房间"
- D_Repair_Log（维修日志表）：严格 1:1 依赖"报修单"
- D_Violation_Record（违纪记录表）：基于"学生"违规行为
- D_Utility_Fee（水电账单费）：依托于"房间"的周期性费用
- D_Water_Order（订水记录）：依托于"房间"的消费事件
- D_Notice（系统公告）：由"管理员"发布的广播事件
- D_Late_Entry（晚归登记）：依托于"学生"的异常时间记录
- D_Leave_Application（离校申请）：依托于"学生"发起的事件
- D_Parcel_Record（快递记录）：连接"学生"与外部物流

**9.2.3 纯联系集**（连接两个强实体的菱形，物理化时转化为表）
- D_Bed_Allocation（住宿分配）：连接"学生"与"房间"的多对多（M:N）联系
- D_Access_Log（门禁刷卡）：连接"学生"与"楼栋"的活动记录
- D_Hygiene_Record（卫生检查）：连接"房间"与"管理员"的管理互动
- D_Visitor_Log（访客登记）：连接"外部人员"与"楼栋"的安全事件

**9.2.4 四种经典对应关系**
1. **一对多（1:N）**：D_Building(1)——隶属于——D_Room(N)；D_College(1)——包含——D_Major(N)。
2. **多对一（N:1）**：D_Student(N)——就读于——D_Major(1)；D_Repair_Ticket(N)——提交自——D_Student(1)。
3. **多对多（M:N）**：D_Student(M)——住宿分配——D_Room(N)。处理方式：引入联系集表 **D_Bed_Allocation** 同时包含 Student_ID 和 Room_ID，化解多对多冲突。
4. **一对一（1:1）**：D_Repair_Ticket(1)——对应——D_Repair_Log(1)。处理方式：在 D_Repair_Log 表中将主键（或加 Unique 约束的外键）直接关联到 Ticket_ID，确保不重复处理。

## 1. 团队构成与分工总原则

团队 10 人按 **"核心设计 + 独立模块开发 + 汇总支持"** 的结构划分。核心原则：**复杂度高、涉及跨模块共享状态或并发控制的部分，由固定人员统一设计和把关；边界清晰、相对独立的功能模块，分配给具体负责人独立完成，并通过锁定的接口契约保证对接质量。**

| 组别 | 角色 | 人数 | 说明 |
|---|---|---|---|
| 统筹与架构组 | 项目经理（组长） | 1 | 进度 / PRD / 验收 / 考勤 |
| 统筹与架构组 | 系统架构师 / 主程 | 1 | 数据库 / 后端骨架 / 公共服务 / 评审 |
| 技术核心攻坚组 | 前端核心专家 | 1 | 脚手架 / 通用组件 / 联调 |
| 技术核心攻坚组 | 后端及数据库核心 | 1 | JWT / 存储过程 / SQL 优化 / 评审 |
| 技术核心攻坚组 | 全栈兼运维专家 | 1 | Docker / 样板间 / 云端部署 / 流水线 |
| 技术核心攻坚组 | 业务疑难点负责人 | 1 | 6 个高难点功能（可与其他角色合并） |
| 独立模块开发组 | 模块负责人 | 4–5 | 认领 8 个模块，每人 1–2 个，并行开发 |

> 若难点负责人与后端核心合并，则模块组为 5 人；否则模块组 4 人、每人认领 2 个模块。

**分工原则**：
1. 每个模块的接口结构（URL、请求/响应字段）在开发前由架构组和项目经理统一锁定在 **Apifox** 中，模块负责人按契约实现，**不自行更改结构**。
2. 涉及**定时任务、并发锁、事务联动、跨模块状态读写**的部分，一律调用统一封装的**公共基础服务**，模块负责人**不自行实现底层逻辑**。
3. 全组在各自模块开发完成后，共同参与系统**黑盒集成测试、性能压测**，并负责编写**课程结题报告、用户手册**等交付文档。

## 5. 并行与串行依赖关系

### 5.1 可以并行（同时开工，互不阻塞）

- **P1｜建库 ／ 前端脚手架 ／ 后端骨架 ／ 运维环境** — 架构师 / 前端 / 后端 / 运维，步骤 1 同时开工。
- **P2｜四大公共服务**（调度 / 通知 / 信用分 / 文件存储）— 架构师（可协调后自行串行，或分给攻坚组并行），步骤 2–5。
- **P3｜各功能模块开发之间** — 模块组 4–5 人，步骤 3 起并行。
- **P4｜难点 1–5 与模块开发** — 难点负责人 + 模块组，步骤 2–7 并行。
- **P5｜云端环境准备 ／ 模块功能开发** — 运维 + 模块组，步骤 6 并行。

### 5.2 必须串行（有先后顺序，前一步没完成后面没法做）

- **S1｜公共服务 → 模块开发** — 模块要调公共服务，形态未定会返工；模块开发建议步骤 3 之后全面启动。
- **S2｜样板间 → 模块开发** — 模块照样板间写，样板间未通会各写各的；样板间步骤 5 发布，模块步骤 5–6 全面铺开。
- **S3｜契约锁定 → 前端页面** — 前端按契约字段做，未锁定会返工；契约步骤 5 全量锁定。
- **S4｜难点 6 退宿清算 → 水电分摊 / 共享借用 / 快递稳定** — 退宿要汇总这些模块的数据状态；难点 6 在步骤 7 启动。
- **S5｜模块完成 → 集成测试** — 黑盒集成要全模块在 develop 上；集成测试在步骤 9。
- **S6｜集成测试通过 → 云端正式部署** — 演示环境必须基于测过的版本；正式部署在步骤 9–10。
- **S7｜功能完成 → 四件套文档 / PPT** — 文档要反映最终实现；集中写作在步骤 10。

### 5.3 一句话总结顺序

> 阶段一：**地基四线并行 → 公共服务 → 契约 + 样板间 → 模块起步**。
> 阶段二：**模块并行攻坚 → 难点收尾 → 集成 → 测试 → 部署 → 文档答辩**。

## 6. 角色依赖关系详细分析（依赖 0–9）

**结论：存在，且贯穿全程。** 大量角色的工作必须建立在其他角色的产出之上，若前置工作未按期完成，后置工作无法开工或会返工。以下按依赖方向列出全部串行关系（依赖 0 为前置阶段依赖，依赖 1–9 沿用 S1–S7 展开）。

### 依赖 0：全体 → 运维（GitHub 仓库）
- **内容**：全员的 Git 提交留痕（考勤与工作量证据）、PR 流程、环境截图验收，都以 **GitHub 仓库**存在为前提。
- **影响**：仓库未建则无人可提交代码，步骤 1 的"提交首个 PR"等验收无从谈起。
- **约束**：运维在**步骤 0（前置阶段）**建仓 + 配分支保护 + 全员 SSH 连通。

### 依赖 1：模块组 → 架构师（公共服务）
- **内容**：模块组的功能代码要调用架构师的**四大公共服务**（调度 / 通知 / 信用分 / 文件存储）。定时任务、并发锁、事务、跨模块读写一律走公共服务，是全员流程红线。
- **影响**：服务接口形态未定型就开发模块，会大面积返工。
- **约束**：公共服务步骤 2–5 完成，模块功能开发**步骤 3 之后**才全面启动。

### 依赖 2：模块组 → 运维（标准样板间）
- **内容**：模块组要照运维发布的**标准样板间**（前后端 + 库跑通的全套写法）写自己的模块代码，统一风格。
- **影响**：样板间未跑通则各写各的，代码风格与结构不一致，后期合并成本高。
- **约束**：样板间步骤 5 发布，模块开发**步骤 5–6** 全面铺开。

### 依赖 3：前端（前端核心 / 模块组）→ 架构师（契约）
- **内容**：所有前端页面要按架构师在 **Apifox 锁定的接口契约**（URL / 请求 / 响应字段 / 鉴权）开发，不许私自修改。
- **影响**：契约未锁定就做页面，字段对不上会返工。
- **约束**：契约步骤 5 全量锁定，前端页面开发须在其之后全面展开。

### 依赖 4：难点负责人 → 架构师（表结构 / 调度框架）+ 模块组（业务数据）
- **内容**：
  - 难点 1 水电分摊、难点 3 防冲突锁的设计，建立在架构师确认的**表结构扩展清单**之上；
  - 难点 5 SLA 派单依赖**调度框架**（Quartz）；
  - 难点 6 退宿清算要汇总**水电分摊、共享借用、快递**等模块的数据状态，需这些模块先行稳定。
- **约束**：难点 6 依赖依赖 4 所列模块，**步骤 7 才启动**；难点 1→6 严格按顺序推进。

### 依赖 5：后端核心 → 前端核心（联调）
- **内容**：后端核心的 **JWT 登录**需要与前端核心的登录页、`request.js` 联调验证（步骤 4）。
- **影响**：登录链路是其他功能验证的前提，此环节不通用影响全员自测。

### 依赖 6：模块组（报表模块）→ 后端核心（报表视图）
- **内容**：模块组「保洁巡检 + 统计报表」的可视化页面，依赖后端核心在步骤 7 编写的**存储过程 / 视图**。
- **约束**：报表视图先行，报表页面在其后完成。

### 依赖 7：全员 → 模块组（模块完成）
- **内容**：步骤 9 的**黑盒集成测试**（学生端 + 管理员端全流程）要求所有模块已合入 develop 分支。
- **约束**：集成测试在步骤 9 统一进行，晚于模块收尾（步骤 8）。

### 依赖 8：运维 → 全员（集成测试通过）
- **内容**：运维的**云端正式部署 / 演示环境**必须基于测试通过的版本，不能拿未测版本上线。
- **约束**：集成测试通过（步骤 9）之后，正式部署在步骤 9–10。

### 依赖 9：项目经理 → 全员（功能完成）
- **内容**：项目经理汇总的**四件套文档与答辩 PPT** 要反映最终实现，必须等全部功能稳定后才能成稿。

## 9. 开发工作流设计

```
[本地 Docker Oracle 21c 环境开发]
        ↓
[各自功能分支 feature/xxx] -> 本地编译自测
        ↓
[提交 Pull Request] -> 模块负责人所在小组内部初审
        ↓
[架构师 Code Review 终审] -> 合并至集成测试分支 develop
        ↓
[云端 Docker 自动化部署] -> 最终发布至 master 分支
```

### 9.1 环境同步流程
- **后端**：项目根目录锁定 .NET SDK 版本，依赖项统一通过 NuGet 声明在 `.csproj` 中；严禁提交敏感配置，一律采用本地 **User Secrets** 隔离。
- **前端**：锁定 Node.js 版本，共享 `.vscode` 配置文件夹，通过 **ESLint 与 Prettier** 强制保存时自动格式化，确保代码风格统一。

### 9.2 契约驱动流程
前后端编码前，必须基于业务需求在 **Apifox** 中定义好完整接口（规范 URL、请求/响应 JSON 结构）。接口锁定后，**前端通过 Mock 数据并行开发，后端按契约编写逻辑**。任何字段或结构变更需先在契约平台同步，**不允许私自修改后再补文档**。

### 9.3 分支管理流程（Git Flow 裁剪版）
- **master 分支**：保持稳定，仅用于生产环境部署，**只有架构师有合并权限**。
- **develop 分支**：日常开发集成分支。
- **feature/xxx 分支**：开发人员各自的功能分支，完成后提交 PR。

### 9.4 两级评审机制
为降低架构师单人评审 10 人代码的瓶颈压力，PR 先由**技术核心攻坚组成员做一轮预筛**（检查是否符合契约、有无明显异常处理缺失），再由**架构师做最终技术评审**后方可合入 develop。

## 10. 说明：功能取舍与计划调整

1. **统一公共服务优先于业务模块并行推进**：后台任务调度框架、通知中心、信用分服务、文件存储方案这四项作为基础设施，**必须在架构组阶段先行交付**，各业务模块开发不得早于这些公共服务确定接口形态，否则后续会出现重复造轮子和数据不一致的返工风险。
2. **高复杂度需求集中管理**：水电分摊、账单划扣断电、设施防冲突锁、库存事务联动、维修派单 SLA、退宿清算这六项涉及并发、事务或跨模块聚合校验，**统一由技术核心攻坚组内固定人员负责设计与实现**，其余模块通过调用封装接口使用，不再各自实现底层逻辑，以降低数据一致性风险。
3. **退宿清算模块的开发时序依赖**：由于该功能需要汇总水电分摊、共享物品借用等多个模块的数据状态，**排期上应明确安排在相关前置模块基本稳定之后启动**，避免过早开工导致接口反复变更。
4. **进度吃紧时的功能裁剪优先级建议**：若中期评估发现整体进度落后，建议**优先精简"SLA 自动升级预警""保洁巡检自动生成"等锦上添花但不影响核心业务演示的功能**，优先保障水电分摊、防冲突预约、报修流转、信用分体系等核心卖点模块的完整度。
5. **贡献记录留痕**：建议全程基于 **Git commit 记录**各功能模块的开发过程，作为后续结题报告或工作量说明的依据。

# 附录 B　建库 SQL 全量脚本（《数据库SQL语言版》）

> 来源：《数据库SQL语言版.txt》。共 20 张表，按依赖关系分四部分顺序创建。执行前先建表空间与专用用户。

```sql
-- ==========================================
-- 第一部分：基础架构与物理空间模块 (无外键依赖，优先创建)
-- ==========================================

-- 1. 学院表
CREATE TABLE D_College (
    College_ID NUMBER(10) PRIMARY KEY,
    College_Name VARCHAR2(100) NOT NULL,
    Counselor_Name VARCHAR2(50),
    Contact_Phone VARCHAR2(20)
);

-- 2. 楼栋表
CREATE TABLE D_Building (
    Building_ID NUMBER(10) PRIMARY KEY,
    Building_Name VARCHAR2(50) NOT NULL,
    Building_Type VARCHAR2(20) NOT NULL,
    Total_Floors NUMBER(3)
);

-- 3. 宿管/管理员表
CREATE TABLE D_Admin (
    Admin_ID VARCHAR2(20) PRIMARY KEY,
    Admin_Name VARCHAR2(50) NOT NULL,
    Phone VARCHAR2(20),
    Role_Level VARCHAR2(20) NOT NULL
);

-- ==========================================
-- 第二部分：次级实体模块 (依赖第一部分)
-- ==========================================

-- 4. 专业表
CREATE TABLE D_Major (
    Major_ID NUMBER(10) PRIMARY KEY,
    College_ID NUMBER(10),
    Major_Name VARCHAR2(100) NOT NULL,
    FOREIGN KEY (College_ID) REFERENCES D_College(College_ID)
);

-- 5. 房间表
CREATE TABLE D_Room (
    Room_ID NUMBER(10) PRIMARY KEY,
    Building_ID NUMBER(10),
    Room_Number VARCHAR2(20) NOT NULL,
    Capacity NUMBER(2) DEFAULT 4,
    Occupancy NUMBER(2) DEFAULT 0,
    FOREIGN KEY (Building_ID) REFERENCES D_Building(Building_ID)
);

-- 6. 系统公告表
CREATE TABLE D_Notice (
    Notice_ID NUMBER(10) PRIMARY KEY,
    Admin_ID VARCHAR2(20),
    Title VARCHAR2(100) NOT NULL,
    Content VARCHAR2(1000) NOT NULL,
    Publish_Time DATE NOT NULL,
    FOREIGN KEY (Admin_ID) REFERENCES D_Admin(Admin_ID)
);

-- 7. 访客登记表
CREATE TABLE D_Visitor_Log (
    Visitor_ID NUMBER(10) PRIMARY KEY,
    Building_ID NUMBER(10),
    Visitor_Name VARCHAR2(50) NOT NULL,
    Visit_Reason VARCHAR2(200) NOT NULL,
    Entry_Time DATE NOT NULL,
    Leave_Time DATE,
    FOREIGN KEY (Building_ID) REFERENCES D_Building(Building_ID)
);

-- ==========================================
-- 第三部分：核心业务与人员模块 (依赖前两部分)
-- ==========================================

-- 8. 学生表
CREATE TABLE D_Student (
    Student_ID VARCHAR2(20) PRIMARY KEY,
    Name VARCHAR2(50) NOT NULL,
    Gender VARCHAR2(10),
    Major_ID NUMBER(10),
    Phone VARCHAR2(20),
    FOREIGN KEY (Major_ID) REFERENCES D_Major(Major_ID)
);

-- 9. 资产明细表
CREATE TABLE D_Asset (
    Asset_ID NUMBER(10) PRIMARY KEY,
    Room_ID NUMBER(10),
    Asset_Name VARCHAR2(50) NOT NULL,
    Quantity NUMBER(3) DEFAULT 1,
    Status VARCHAR2(20) NOT NULL,
    FOREIGN KEY (Room_ID) REFERENCES D_Room(Room_ID)
);

-- 10. 水电费账单表
CREATE TABLE D_Utility_Fee (
```

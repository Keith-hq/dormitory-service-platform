## 一、架构概览

### 业务流程

```
每月1号 0:05  → SP_Auto_Deduct(attemptNo=1) → 第1次扣款 → 够则扣，不够记录
每月2号 0:05  → SP_Auto_Deduct(attemptNo=2) → 第2次扣款 → 再试
每月3号 0:05  → SP_Auto_Deduct(attemptNo=3) → 第3次扣款 → 最后一次机会
每月3号 0:10  → SP_Check_Power_Cut          → 3次都失败+电费未缴 → 断电
每分钟        → SP_Restore_Power             → 断电房间全员缴清 → 恢复
```

### 核心规则

- 扣款只看 D_Wallet_Account.Balance，够则全扣，不够一分不扣
- 断电只看电费（Power_Share），水费欠缴不触发断电
- 断电断整个房间（一个人欠费全屋断电），缴费后5分钟内自动恢复
- 幂等保证：UK_D_WALLET_LOG_KEY 防重复扣款，UK_D_FEE_DED_ATT 防重复记录

### 2.2 存储过程：SP_Auto_Deduct

**文件**：`database/sp/sp_billing.sql`

**参数**：

| 参数 | 类型 | 说明 |
|---|---|---|
| p_AttemptNo | NUMBER | 第几次尝试（1、2、3） |
| p_YearMonth | VARCHAR2 | 账单月份，如 '2026-08' |

**调用方式**：`BEGIN SP_Auto_Deduct(1, '2026-08'); END;`

**处理流程（v1.3 原子认领）**：

1. 遍历当月所有 Is_Paid='否' 且已发布的 D_Fee_Detail（JOIN D_Utility_Fee 获取月份，排除 0 元）
2. SAVEPOINT + 原子认领：`UPDATE D_Fee_Detail SET Is_Paid='是' WHERE Detail_ID=:id AND Is_Paid='否'`——ROWCOUNT=0 说明并发已被他人缴，静默跳过（不扣款、不记尝试）
3. 原子扣款：`UPDATE D_Wallet_Account SET Balance=Balance-due WHERE Student_ID=:sid AND Balance>=due`
4. 余额不足/钱包行不存在 → 回滚认领（明细保持未缴，下轮重试），只记录 Attempt（余额不足）
5. 扣款成功 → 写 D_Wallet_Log（Transaction_Type='自动扣款'，Idempotency_Key 防重）→ 记录 Attempt（成功）
6. 幂等：UK_D_WALLET_LOG_KEY 冲突时静默跳过；UK_D_FEE_DED_ATT 冲突时 UPDATE 覆盖旧状态
7. 锁序与 SP_Manual_Pay v1.1 一致（明细→钱包），两 SP 并发无 ORA-00060

### 2.3 存储过程：SP_Check_Power_Cut

**调用方式**：`BEGIN SP_Check_Power_Cut('2026-08'); END;`

**处理流程**：

1. 找出当月 Power_Share > 0 且 Is_Paid='否' 的分摊
2. 子查询确认该分摊的第 3 次 Attempt 结果为"余额不足"
3. 将对应房间的 Power_Status 置为"断电"

### 2.4 存储过程：SP_Restore_Power

**调用方式**：`BEGIN SP_Restore_Power; END;`

**处理流程**：

1. 取当前月份（SYSDATE）
2. 扫描所有 Power_Status='断电' 的房间
3. NOT EXISTS 检查：该房间本月是否不存在未缴电费账单
4. 全部缴清 → Power_Status 置为"正常"

## 七、缴费与钱包接口（2026-08-15 落地）

对应集成测试用例 C3 缴费划扣链路（IT-C3-001 ~ 004）的接口层落地。

### 7.1 存储过程：SP_Manual_Pay（人工缴费，STU-05）

**文件**：`database/sp/sp_wallet.sql`（依赖 sp_billing.sql 的 SEQ_WALLET_LOG，不内联 DDL）

**签名**：

```sql
PROCEDURE SP_Manual_Pay(
    p_Detail_ID       IN NUMBER,     -- 分摊明细 ID（DORM-23 返回的 detailId）
    p_Student_ID      IN VARCHAR2,   -- 缴费学生学号（C# 已校验为当前登录学生）
    p_Idempotency_Key IN VARCHAR2,   -- 幂等键（≤100 字符）
    p_Result_Code     OUT NUMBER
)
```

**结果码**：

- 0 = 成功或幂等重放（同 Key 同主体已成功过 / 并发同 Key 由对方先行提交）
- 1 = 明细不存在
- 2 = 明细非本人（Detail 的 Student_ID 与 p_Student_ID 不符）
- 3 = 余额不足（钱包行不存在同此——缴费不自动开户；并发同 Key 兜底也可能返回）
- 4 = 已缴或明细金额为 0（不同 Key 重复缴 / 并发已被他人缴 / 无需缴；认领 UPDATE ROWCOUNT=0 裁决）
- 5 = Idempotency-Key 已被其它交易占用（类型不同 / 同 Key 不同学生或明细，P2-5 主体比对整改）

**流程（v1.1 原子认领）**：幂等重放检查（比对 Transaction_Type+Student_ID+Detail_ID 三主体，必须先于任何业务校验）→ 明细校验（rc=1/2）→ 0 元（rc=4）→ SAVEPOINT + 原子认领（`UPDATE D_Fee_Detail SET Is_Paid='是' WHERE Detail_ID=:id AND Is_Paid='否'`，ROWCOUNT=0 → 回滚 rc=4）→ 原子扣款（`UPDATE ... WHERE Balance >= due`，ROWCOUNT=0 → 回滚认领 rc=3）→ 写流水（UK 冲突 → 回滚认领+扣款，读对方已提交流水比对主体：同主体 rc=0 / 不同主体 rc=5）→ COMMIT。

### 7.2 存储过程：SP_Recharge（充值，STU-07）

**签名**：

```sql
PROCEDURE SP_Recharge(
    p_Student_ID      IN VARCHAR2,
    p_Amount          IN NUMBER,     -- 充值金额（>0）
    p_Idempotency_Key IN VARCHAR2,
    p_Result_Code     OUT NUMBER
)
```

**结果码**：

- 0 = 成功或幂等重放（同 Key 同学生已成功过 / 并发同 Key 由对方先行提交）
- 1 = 金额为空或 ≤0，或加款后超出余额上限 NUMBER(8,2)
- 2 = 幂等键已被其它交易占用（类型不同 / 同 Key 不同学生，P2-5 主体比对整改）
- 3 = 学生不存在（D_Student 无该学号，FK -2291；正常流程 C# 已拦截）

**流程（v1.1）**：幂等重放检查（比对 Transaction_Type+Student_ID）→ 金额校验（rc=1）→ MERGE 自动开户（学生不存在 -2291 → rc=3）→ SAVEPOINT + 加余额（溢出 ORA-01438 → rc=1）→ 写流水（UK 冲突 → 回滚加款，读对方已提交流水比对主体：同学生 rc=0 / 不同学生 rc=2）→ COMMIT。

### 7.3 幂等与并发语义（联调必读）

- 幂等键 = `D_Wallet_Log.Idempotency_Key`（UK_D_WALLET_LOG_KEY 唯一约束），与 C# `Idempotency-Key` 请求头同源，≤100 字符。
- 同 Key 顺序重试：重放检查在任何业务校验之前，直接返回 rc=0（例如已缴明细用原 Key 重试返回成功，而不是 rc=4）。**重放检查与撞 UK 兜底均比对业务主体**（缴费=类型+学生+明细，充值=类型+学生）：同 Key 被不同主体复用不返回假成功（缴费 rc=5 / 充值 rc=2）。
- 同 Key 并发双提交（线性化兜底）：两个会话同时通过重放检查后，后提交者的流水 INSERT 撞 UK，ROLLBACK TO SAVEPOINT 撤销本会话的认领/扣款（加款）后读对方已提交流水比对主体：同主体 → rc=0，不同主体 → rc=5/rc=2。因此**同 Key 重试 rc=0 或 rc=3 均为交易已终态**，余额以钱包查询（STU-06）为准。
- 不同 Key 并发缴费（人工 vs 人工 / 自动 vs 人工）：以 D_Fee_Detail 的**原子认领**为唯一权威——`UPDATE Is_Paid='否'→'是'` 的 SQL%ROWCOUNT 裁决唯一赢家，败者 ROWCOUNT=0 → rc=4（已缴），杜绝双重扣款。锁序统一为明细→钱包（与 SP_Auto_Deduct v1.3 同序），两 SP 并发无 ORA-00060 交叉锁死锁。
- 跨类型 Key 冲突：缴费 SP 返回 rc=5、充值 SP 返回 rc=2（Key 被另一种交易占用），比常规设计多两个码，联调时按上表映射即可。

### 7.5 SP 并发整改修订记录（PR #58 评审，2026-08-15）

- **v1.1/v1.0 的问题（P1-2 双重扣款）**：人工缴费先扣钱包后标记 Is_Paid，两个不同 Key 的并发缴费（或自动扣款与人工缴费并发）都能先读到 Is_Paid='否' → 双重扣款。
- **v1.2 修复（已废弃）**：SP_Auto_Deduct 的原子 UPDATE 追加 Is_Paid='否' 子查询复查。方向对但锁序与人工缴费相反（自动先钱包后明细、人工先明细后钱包），两 SP 并发存在 ORA-00060 交叉锁死锁风险。
- **v1.3 / sp_wallet v1.1（最终方案）**：两 SP 统一升级为"原子认领"——先 `UPDATE D_Fee_Detail SET Is_Paid='是' WHERE Is_Paid='否'`，SQL%ROWCOUNT 裁决唯一赢家，败者 rc=4/静默跳过；锁序统一为明细→钱包，无交叉锁死锁；余额不足回滚认领保持明细未缴；自动扣款对"并发已被他人缴"静默跳过（不再误记'余额不足'尝试）。
- **P2-5 幂等主体比对**：重放检查与撞 UK 兜底均比对业务主体（缴费=类型+学生+明细，充值=类型+学生），同 Key 被不同主体复用不返回假成功。
- **验证**：test_sp_wallet.sql 49 断言（T15 人工先自动后 / T16 自动先人工后 / T17 人工 vs 人工双方向，2026-08-15 Oracle 实测 49/49 PASS）；test_sp_checkout_fee.sql 回归 16/16 PASS。

### 7.6 接口层实现要点

- 缴费/充值走 `CommandType.StoredProcedure` + OUT `p_Result_Code` 读结果码（照抄 SlaDispatchService.CallResultCode 模式）；SP 自 COMMIT，C# 不包事务。
- 录账单 Fee_ID 由 026 迁移的序列触发器回填，EF 侧 `ValueGeneratedOnAdd()` + RETURNING 读回（与 Room 同模式）。
- 修改用条件 UPDATE（`WHERE NOT EXISTS 明细`，防并发分摊抢先）；发布用条件 UPDATE（`WHERE Publish_Status='未发布'`，防并发发布抢先）；SQL%ROWCOUNT 守门。

- 单元测试：173/173 通过（PR #58 整改后新增：DORM-24 过滤/分页/参数校验、必填兜底、低余额提醒、已分摊禁改；STU-04 联表投影/账期过滤/越权 403/非法 yearMonth 400）。
